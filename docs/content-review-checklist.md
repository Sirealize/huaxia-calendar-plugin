# 内容发布审核清单

> 适用对象：`packages/content-l1/**` 的「每日文明史叙事」条目，以及未来任何随包分发或在线推送的文本内容（卦象解读、节令文案、专题扩展包）。
> 权威依据：`docs/evaluation/内容层可行性.md`（第三节筛选标准、第四节合规边界）与 `packages/core/src/data/schemas.ts`（许可证铁律）。
> 原则：**准确性优先于丰富度；不确定宁可不写。年份写错是产品事故。**

---

## 0. 一页速查（每条内容都必须全部打勾）

- [ ] 这是**原创整理**或**公有领域**内容，没有 CC BY-SA、维基正文、百度百科正文
- [ ] `source` 已填（自撰写「原创整理」），`license` 只取 `self-authored` / `public-domain`
- [ ] `retrievedAt` 已填 ISO 日期；引用公有领域原文时 `sourceUrl` 已填或注明版本出处
- [ ] 年份经过**至少两个独立来源**交叉核对，其中至少一个是权威来源
- [ ] 日期口径已确认（事件当地日期 / UTC / 北京时间），跨日事件已按原始记录归档
- [ ] 无预测、占卜、吉凶、宜忌、财运、姻缘、健康类表述（见 §3 红线词表）
- [ ] 民族、宗教表述使用规范名称，不评价教义，不涉及敏感事件（见 §4）
- [ ] `summary` 60–140 字，`title` 8–20 字，说清「哪年 + 发生了什么 + 为什么值得记一笔」
- [ ] 不写帝王家事、宫廷斗争、战争细节、当代政治评价；无煽情、无夸张断言
- [ ] `node --test` 与 manifest 构建全部通过（见 §6）

## 1. 许可证合规（发布闸门，一票否决）

| 项 | 要求 |
|----|------|
| 允许的 `license` | 仅 `self-authored`（原创文案）与 `public-domain`（已过版权保护期的原文，如《周易》经文） |
| 禁止的许可证 | `CC-BY-SA-4.0`（相同方式共享会传染整个内容包），以及 `unknown`、空白、无许可证来源 |
| 禁止的内容来源 | 维基百科/维基数据正文、百度百科、互动百科等百科站正文；任何无 LICENSE 的「历史上的今天」数据集；受版权保护的白话译本 |
| 允许的参考来源 | 官方机构与国家级媒体、学术机构与权威辞书、公有领域古籍原文（仅可引用原文，白话解释必须原创） |
| 来源字段 | `source` 必填；`sourceUrl` 在引用网页/数据库时填写；`retrievedAt` 必填 ISO 日期 |
| 署名义务 | 仅 CC 许可需要 `attribution`；本项目不使用 CC 许可，`manifest.attribution` 仍需声明整体为 self-authored |

> 判定不下来的，按「不能用」处理。违反本节的条目不得进入发布包，`validateContentPack()` 会阻断。

## 2. 年份与史实核实流程（准确性红线）

1. **列候选**：先把「日期 + 年份 + 事件 + 一句话意义」写成草稿，不确定的候选直接丢弃，不要先写正文再补年份。
2. **双源交叉**：至少 2 个**相互独立**的来源；其中至少 1 个为权威来源（国家部委/官方机构、国家级媒体、高校或学术机构、权威辞书、当事人档案）。两个来源不能互相转抄（例如两个聚合站同抄一条维基不算双源）。
3. **确认日期口径**：区分事件发生地当地时间与 UTC；境外事件可能跨日。本产品按北京时间展示，归档仍以**事件原始记录日期**为准；若两种口径会落在不同日期，选择无歧义的一天，或在 `summary` 内注明口径（如「当地时间」）。
4. **置信度自评**：
   - 高：能复述来源与关键细节，来源间无冲突 → 可发布
   - 中：方向确定但日期/细节需再核 → **不得发布**，继续核或换条
   - 低：凭印象 → **直接换条**
5. **记录核校证据**：审核人在发布记录里写下核对过的来源（链接或书名+版次+页码），而不只是打勾。
6. **二次独立核对**：内容作者与审核人不得是同一人的「自我确认」；发布前由另一人独立复核年份。

**典型易错点**：把「发明完成年份」写成「专利批准日」；把「首次公开演示」写成「发明日」；把 UTC 日期直接当北京时间；把「某年」当成「某月某日」；将传记生日当作事件日。

## 3. 合规红线词表（占卜 / 预测类，禁止出现在任何内容与 UI 文案）

| 禁止类别 | 禁止词/表述（含近义变体） | 允许的替代表述 |
|----------|--------------------------|----------------|
| 吉凶宜忌 | 宜、忌、吉、凶、大吉、大凶、凶兆、祥瑞断语、今日宜/忌 | 仅陈述历史事实与文明史意义 |
| 运势预测 | 运势、时运、开运、转运、好运、厄运、命中注定、预示、征兆 | 不预测个人未来 |
| 财运 / 姻缘 | 财运、进财、破财、姻缘、桃花运、正缘、合婚、感情运 | 不涉及个人事项 |
| 健康 / 学业 | 健康运、疾病预测、考试运、升迁运、官司运 | 不涉及个人事项 |
| 术数操作 | 占卜、算命、摇卦、起卦、解卦、抽签、看相、风水、化解、消灾、本命年禁忌 | 传统文化知识介绍；明确注明「非预测建议」 |
| 伪科学断言 | 「科学证明」式玄学、必然因果断言、绝对化预测 | 使用「据记载」「史料表明」等可核查表述 |

> 说明：卦象（F08）不在 M0′ 范围；未来若上线，只允许「卦名/卦画/卦辞/爻辞原文 + 原创义理解读 + 常驻免责声明：传统文化知识，不构成任何预测或建议」，且必须保留 `compliance.prophecyEnabled = false` 开关的降级路径。

## 4. 民族与宗教表述规范

- 使用**规范全称**：行政区划、民族名称、宗教名称使用国家规范表述，不使用旧称、俗称或贬称（如不用「回教」「穆民」等旧称指代伊斯兰教/穆斯林）。
- **不评价教义**：只做历史与文明史层面的客观陈述，不对宗教教义作真伪、高低、优劣判断。
- **不涉及敏感事件**：不写民族冲突、宗教冲突的细节与归因；不转载境外对民族宗教事务的评论。
- **不搞身份标签**：不以民族、宗教身份给人物贴标签；涉及多民族共同历史时使用「各民族」等规范表述。
- **古籍引用**：引用古籍原文可保留历史用语，但须注明出处与时代背景，不得借此输出歧视性或贬损性表述。
- **地名与称谓**：历史地名可保留，但需与今地名对应清楚；涉及边界、领土表述严格使用国家规范用语。
- 拿不准的敏感条目：**换条**，不要试探边界。

## 5. 内容质量与文风

- **三要素齐全**：年份 + 事件 + 一句话文明史意义，缺一不发布。
- **文明史视角**：优先科学发现、技术发明、工程竣工、法典/制度颁布、文化作品问世、重大公共事件；避开帝王家事、宫廷斗争流水账、战争细节、当代政治评价。
- **长度**：`summary` 60–140 字（按 Unicode 码点计），`title` 8–20 字；`summary` 超过 140 字先删修饰，不删事实。
- **文风**：陈述事实，不煽情、不感叹、不使用「最伟大」「彻底改变世界」等夸张断言；不出现「今天我们应该……」式说教。
- **可读性**：一屏可读，避免生僻专名堆砌；数字与年代使用阿拉伯数字（如「1883 年」）。
- **排序权重**：同一天多候选取文明史价值最高者；`weight` 0–100，仅在同日多条时用于排序。

## 6. 发布前必跑（内容包）

```bash
export npm_config_cache=/tmp/npmcache-huaxia
cd packages/content-l1
node scripts/build-manifest.mjs   # 用脚本重算 bytes / sha256 / counts，禁止手填
node --test                       # 8 项闸门测试必须全绿
```

测试断言覆盖：

1. 30 条、覆盖 11-18 至 12-17、每天恰一条、id 唯一且与月日一致
2. 逐条通过 `validateHistoricalEvent`（schema）
3. `license` 白名单（`self-authored` / `public-domain`）与 `source`/`retrievedAt` 齐全
4. `summary` 60–140 字、`title` 8–20 字、`yearLabel` 与 `eventYear` 一致
5. `manifest` 的 counts 与数据一致
6. `manifest.files` 的 `bytes` / `sha256` 与数据文件实测值一致
7. `validateContentPack` 精确断言：M0′ 包 errors 恰好 1 条且只能是「hexagrams 64 卦不完整」
8. `assertContentPack` 发布闸门只报卦象缺口，不混入历史事件条目问题

> 第 7 条是哨兵：将来补上卦象后它会主动失败，提醒同步更新测试与 `counts.hexagrams`。

## 7. manifest 更新规则

- `packVersion`：按内容变更幅度递增；M0′ 固定 `0.1.0-m0.0`。
- `counts`：必须等于实际数组长度（`hexagrams: 0` 时不得写 64）。
- `files[].bytes` / `files[].sha256`：**只能由 `scripts/build-manifest.mjs` 计算**，任何手填值都视为不合格。
- `generatedAt`：默认保留既有值以保证可复现；需要更新时用 `PACK_GENERATED_AT=<ISO>` 显式覆盖。
- `coverage.dayOfYearCoverage`：30 天样板为 `partial`，全年补齐后才改为 `full`。

## 8. 审核记录表（每条内容填写，随 PR 提交）

| 字段 | 填写要求 |
|------|----------|
| 条目 id | 如 `he-1124-001` |
| 年份置信度 | 高 / 中 / 低（中、低不得发布） |
| 交叉来源 | ≥2 个，写明来源名与链接/版次页码 |
| 日期口径 | 当地时间 / UTC / 北京时间，跨日说明 |
| 红线词扫描 | 命中 0 次（附扫描方式） |
| 敏感表述检查 | 民族/宗教/当代政治 均无 |
| 审核人 + 日期 | 独立于作者的复核人 |
| 结论 | 通过 / 换条 / 退回修改 |

## 9. M0′ 范围说明

- 覆盖 30 天：公历 11-18 至 12-17，每天恰一条，用于验证「用户会不会每天看这一条」。
- **不含卦象（F08 不在 M0′ 范围）**，`manifest.counts.hexagrams = 0`，`hexagrams: []` 是既定范围而非遗漏。
- 支持范围 1901–2100，展示口径北京时间；内容包内事件的 `eventYear` 可以早于 1901（「历史上的今天」本身就是回看历史）。
- 未来扩到 365 天时：沿用本清单，逐日补条目，`dayOfYearCoverage` 改为 `full`，并同步更新 §6 的测试断言。
