# Phase 0 · 内容层可行性评估

> 评估对象：规划文档中的 F03「每日历史叙事」、F08「八卦与每日卦象」。
> 结论先行：**这两项不是技术问题，是编辑工程，且现成公开数据集的许可证不可直接用于随包分发。**
> 这是规划文档（`docs/整体规划方案.md`）第 5.2 节与风险表未识别到的缺口。

---

## 一、结论速览

| 判断 | 结论 | 置信度 |
|------|------|--------|
| 24 节气 / 农历 / 干支 / 节日日期 | ✅ 可纯算法计算，无需内容数据 | 高（算法层独立验证） |
| 365 天历史叙事 | ⚠️ **必须自撰**，不能直接复用公开数据集 | 高（许可证实测，见第二节） |
| 「每日一卦」的卦名/卦辞/爻辞 | ✅ 《周易》原文属公有领域，可自由使用 | 高 |
| 「每日一卦」的白话解读与工作启示 | ⚠️ 必须自撰，且受合规边界约束（见第四节） | 高 |
| 内容层实际工作量 | 365 条文明史条目 ≈ 30–40 小时编辑工时；不能靠"抓数据"节省 | 中高 |

**对 MVP 的含义**：内容层是唯一无法用工程手段压缩的成本项。**建议 MVP 只交付 30 天精选样板（占全量 8%），验证"用户会不会看"之后再投入剩余 335 天的编辑工时。** 这比先做 365 天再验证便宜一个数量级。

---

## 二、公开数据集许可证核查（实测）

规划文档 5.2 节默认「365 条历史事件可打包进安装包（~500KB）」，但未核查内容来源的再分发许可。实测结论如下：

| 数据集 | 数据量 | 许可证实测 | 能否随插件包分发 |
|--------|--------|-----------|------------------|
| [zhoujinshi/history_in_today](https://github.com/zhoujinshi/history_in_today) | 1.6MB JSON，源自维基百科，2023-05 停止更新 | **无 LICENSE**（GitHub API `license: null`） | ❌ 不能。无许可 = 保留所有权利，默认禁止再分发 |
| [LuoH-AN/TodayInHistory](https://github.com/LuoH-AN/TodayInHistory) | 6.1MB，2026-10 更新，源为维基百科 + 百度 | 仓库声明 MIT，但**正文源自维基（CC BY-SA 4.0）与百度百科** | ❌ 不能干净使用。MIT 只覆盖代码，覆盖不了维基正文的署名+相同方式共享义务，百度内容更是专有版权 |
| 《周易》卦辞/爻辞、《史记》等古籍原文 | — | **公有领域**（著作权已过期） | ✅ 可自由使用、可随包分发 |
| 自撰条目 | — | 本项目自有版权 | ✅ 可自由使用 |

### 关键判断

1. **"抓个开源数据集就完事"这条路走不通。** 两个最常被搜到的中文「历史上的今天」数据集，一个没有许可证，一个是用 MIT 外壳包装了维基 CC BY-SA 与百度百科的内容。把这类数据打包进 `.vsix` / npm 包分发给内网用户，属于再分发 → 触发 CC BY-SA 的署名与相同方式共享义务，百度部分则直接侵权。
2. **维基正文不是不能碰，而是不能批量内嵌。** 若走这条路线，必须：逐条在 UI 展示来源与许可、整个内容包以 CC BY-SA 相同方式共享、且剔除百度来源条目。对一个"内部工具"来说这属于**不必要的法律负担**，且与规划 A3「文明史视角（科技/文化/制度/工程）」的筛选口径并不匹配 —— 维基的"大事记"是泛历史事件的堆砌，不是文明史策展。
3. **因此 F03 的正确做法是：自撰 + 来源可标注。** 内容 schema 必须为每条记录保留 `source` / `license` 字段（已在 `@shishu/core` 数据 schema 中要求落地），使未来替换或引入外部来源时不返工。

## 三、内容供给策略（替代规划的"打包 L1 数据集"）

按"许可可控性"从高到低分三层，与规划的 L1/L2/L3 分层对齐但重新定义来源：

| 层 | 内容 | 来源 | 体积目标 | 何时做 |
|----|------|------|---------|--------|
| **L0 算法层** | 农历、24 节气、干支、节日日期 | 纯算法 | 0 KB 数据 | MVP 必做 |
| **L1 精选** | 30 天 × 1 条文明史叙事 + 64 卦原文 + 解读 | 自撰（古籍原文公有领域） | < 150 KB | MVP 做 30 天样板 |
| **L2 全量** | 365 天全量叙事 | 自撰 | < 500 KB | 验证留存后再补 |
| **L3 扩展包** | 诗词、典故、科技史专题 | 自撰 / 公有领域古籍 | 按需 | 远期 |

### 条目质量门槛（每条必须满足）

- **三要素齐全**：年份 + 事件 + 一句话意义（规划 F03 验收标准）
- **文明史视角**（规划 A3）：优先科技、制度、工程、文化、经济；不选帝王将相的家事与战争流水账
- **可核实**：年份与事件须能对应到公开史料；不确定的宁可不写
- **合规**：不涉及民族宗教敏感表述、不涉当代政治评价
- **长度**：正文 40–80 字（一屏可读，符合规划 S3「30 秒读完」）

### 工作量实测口径

按每条"起草 5 分钟（AI 辅助）+ 核校 5 分钟"计：365 条 ≈ **30–40 小时**净编辑工时，且核校部分难以并行外包给模型（准确性不可自证）。这就是建议先做 30 天的量化理由：30 条 ≈ 3 小时即可交付可体验版本。

## 四、卦象的合规边界裁定（对应规划 A2）

规划风险表把「八卦内容涉嫌封建迷信、内网部署有合规风险」列为 P0。给出可执行的裁定，避免上线前返工：

**定位**：传统文化知识 + 工作方法启示。**不是**占卜。

| 允许 | 禁止 |
|------|------|
| 卦名、卦画、卦辞、爻辞原文（公有领域） | 「今日宜/忌」类断言 |
| 白话翻译与义理解读 | 「吉/凶/大吉/大凶」判断 |
| 由卦象引申的工作方法启示（如「潜龙勿用」→ 准备期不宜冒进） | 财运、姻缘、健康、考试等具体事项预测 |
| 注明"传统文化知识，非预测建议"的常驻说明 | 任何形式的"为你算一卦"交互 |

**实现要求**：
1. UI 上每处卦象内容常驻一行免责说明：`传统文化知识，不构成任何预测或建议`。
2. 代码层提供 `compliance.prophecyEnabled = false` 开关（规划已提到"合规审核开关"，落为具体配置项），开启后仅额外暴露纯原文，不含任何引申义。
3. 内容审核清单进仓库（`docs/content-review-checklist.md`），新增条目必须过清单。

## 五、给 MVP 的具体建议

1. **F03 收窄**：MVP 交付 **30 天精选样板**，而非 365 天全量。验收标准相应改为「样板区间内每天一条且质量过清单」，全年覆盖留到 L2。
2. **F08 后置**：卦象从"MVP 必备"降级为"MVP 可选/二期"。若保留，只做原文 + 义理 + 免责说明，不做任何预测性文案。
3. **内容与代码解耦**：内容包以独立 JSON 目录组织、带版本号与许可证字段，使内容更新不需要发版插件。这条同时满足规划 F06「离线可用」与 F15「内容包订阅」的远期形态。
4. **来源标注机制前置**：现在就把 `source`/`license` 字段做进 schema。规划风险表提到"建立内容来源标注机制"，这正是最低成本的做法。
