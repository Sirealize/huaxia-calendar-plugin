# 华夏文明日历插件 · 整体规划方案

> 基于用户原始诉求，从产品需求和技术架构两条线融合而成的完整规划。
> 核心假设：以 DeepSeek 为首选宿主、MVP 阶段纯展示型、内容定位为「文明史 + 文化启示」而非预测占卜。

---

## 一、项目概览

### 1.1 一句话定位

**一个能装在 AI 编码工具侧边栏/悬浮窗里的华夏文明日历——公历+农历+节气+历史叙事+每日卦象，同时展示每日工作进度、Token 消耗和任务清单，支持 git 安装、内外网运行、离线可用。**

### 1.2 目标用户（核心假设）

| 层级 | 用户画像 | 比例假设 |
|------|---------|---------|
| 核心用户 | 日常深度使用 AI 编码工具（DeepSeek 为主、豆包为辅）的开发者，每天打开 AI 对话 ≥4 小时，关注 token 成本，对传统文化有兴趣 | 70% |
| 次核心用户 | 对华夏文明有兴趣的知识工作者，把插件当"每日一得"文化入口 | 30% |

### 1.3 核心使用场景

| 编号 | 场景 | 触发时机 | 用户目标 |
|------|------|----------|----------|
| S1 | **每日开工校准** | 早晨打开 AI 编码工具时 | 一眼看到公历+农历+节气+历史上的今天，建立当日仪式感 |
| S2 | **工作进度总览** | 每次回到 AI 工具窗口时 | 快速查看今日任务、token 消耗、剩余预算，调整节奏 |
| S3 | **碎片化文化浏览** | 编译等待、模型思考间隙 | 点开当天的八卦/历史叙事，30 秒读完，获得知识增量 |
| S4 | **离线/内网开发** | 隔离内网、飞机、无网环境下编码 | 日历和文化内容依然可用，不依赖外部服务 |
| S5 | **自定义位置摆放** | 不同屏幕布局习惯 | 放在顺手的位置（左栏/角落悬浮/置顶），不遮挡主工作区 |

## 二、宿主可行性结论（2026 年现状）

> 来源：架构侧联网核实，详见技术架构方案文档。结论是——**没有任何一个宿主打满分**，需要组合方案。

| 宿主 | UI 嵌入能力 | Git 安装 | Token 数据 | 优先级 | 备注 |
|------|------------|----------|-----------|--------|------|
| **DeepSeek（含 Harness）** | ✅ 左侧栏 Slot + 悬浮置顶 | ✅ npm + git | ⚠️ 需核实 API | **最高** | 社区文档较成熟，用户最常用 |
| **VS Code / MarsCode / Codex** | ✅ Webview 侧边栏/底部面板/状态栏 | ✅ 原生扩展市场 | ✅ 有 API | 高 | 生态最稳，但 Codex 本身定位需进一步核实 |
| **豆包桌面端** | ❌ 无 UI 扩展点（MCP 仅数据层） | ❌ ZIP 上传 | ⚠️ 需核实 | 低 | UI 嵌入走不通，仅做数据接入（MCP） |
| **纯 Web 版（浏览器扩展/油猴）** | ✅ 侧边栏/悬浮注入 | ✅ 解压加载 | ⚠️ 需拦截请求 | 备选 | 兼容性和稳定性差，作兜底方案 |

**关键判断**：用户说的"豆包"大概率指**豆包 MarsCode（VS Code 系）**而非豆包桌面聊天端，前者有完整扩展机制。需与用户确认。

## 三、功能清单与优先级

### 3.1 MVP（P0 · 必做 · 6-8 周）

> **目标验证**：开发者愿意在 AI 编码工具里常驻一个中国风日历插件。

| 编号 | 功能 | 一句话描述 | 验收标准 |
|------|------|------------|----------|
| F01 | 基础日历视图 | 公历+农历双轨显示，月视图切换、当天高亮 | 公历农历一一对应正确，切换月份无错位，当日有视觉高亮 |
| F02 | 节气与传统节日 | 24 节气标注 + 主要传统节日显示 | 24 节气日期准确，主要传统节日（春节/清明/端午/中秋等8个+）有名称显示 |
| F03 | 每日历史叙事 | 每天一条"历史上的今天"中国历史事件 | 每天至少一条，含年份/事件/简述三要素，全年 365 天无空缺 |
| F04 | 灵活嵌入与位置切换 | 左侧栏嵌入 + 左下角悬浮两种形态，可一键切换 | 两种形态切换流畅，状态被记住，不影响宿主主界面操作 |
| F05 | Git 地址一键安装 | 通过 git clone + 简单命令加载插件 | 按 README 执行 ≤3 条命令完成安装，除 git clone 外不依赖外网 |
| F06 | 离线可用 | 所有日历数据、文化内容、UI 资源打包在本地 | 断网后所有功能正常使用，无降级，无加载失败 |
| F07 | Token 消耗记录 | 手动录入/CSV 导入当日 token 使用量，显示累计与趋势 | 日历上每天显示当日消耗，月视图有月度汇总，保留 ≥90 天历史 |

### 3.2 二期（P1 · 增强 · 6-8 周）

| 编号 | 功能 | 一句话描述 | 验收标准 |
|------|------|------------|----------|
| F08 | 八卦与每日卦象 | 每日一卦，卦画+卦辞+白话解读+工作生活启示 | 内容定位为"文化启示"，不涉及运势预测或吉凶断言 |
| F09 | 任务清单集成 | 今日待办，支持勾选完成，本地持久化 | 添加/勾选/删除正常，完成状态在日历上有可视化标记 |
| F10 | 工作日报生成 | 汇总当日任务+token+时间分布，生成 Markdown 日报 | 一键产出结构化日报，支持复制 |
| F11 | 四角悬浮 + 置顶模式 | 四角任意位置悬浮、窗口置顶、大小可调 | 拖动到四角任意位置，置顶后不被其他窗口遮挡 |
| F12 | 主题皮肤切换 | 多种华夏风格主题（水墨/青铜/简素等） | 至少 3 种主题，切换后全局配色字体装饰同步变化 |

|------|------|------|

## 四、技术架构总览

### 4.1 推荐架构：核心层 + 多宿主适配器（One Core, Many Hosts）

```
┌─────────────────────────────────────────────────────────┐
│                    宿主应用层（Hosts）                    │
│  ┌──────────┐  ┌──────────────┐  ┌───────────────────┐  │
│  │ DeepSeek │  │ VS Code /    │  │ 纯 Web / 浏览器扩展 │  │
│  │ Harness  │  │ MarsCode     │  │（油猴 / Chrome 扩展）│  │
│  └────┬─────┘  └──────┬───────┘  └─────────┬─────────┘  │
│       │ 薄适配器        │ 薄适配器             │ 薄适配器     │
├───────┼────────────────┼─────────────────────┼───────────┤
│       ▼                ▼                     ▼            │
│              统一适配接口层（Adapter API）                  │
│       （slot / webview / overlay / sidebar 抽象）           │
├───────────────────────────────────────────────────────────┤
│                                                           │
│               核心层（Core — Web Components）              │
│  ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐  │
│  │ 日历核心 │ │ 农历算法  │ │ 文化内容  │ │ 工作数据模块  │  │
│  │ 引擎    │ │ 节气/八卦 │ │ 历史/卦象 │ │ Token/任务   │  │
│  └─────────┘ └──────────┘ └──────────┘ └──────────────┘  │
│                       ▲                                   │
│                       │ 本地存储（IndexedDB / localStorage）│
│              纯前端 · 零后端 · 全离线                       │
└───────────────────────────────────────────────────────────┘
```

### 4.2 架构选型理由

| 维度 | 选择 | 理由 |
|------|------|------|
| **核心技术** | Web Components（Lit 或 Stencil） | 原生标准、框架无关、体积小、各宿主通用 |
| **分发方式** | Git 仓库 + 各宿主包管理器 | 满足"git 地址安装"诉求；npm/pip/VSIX 按宿主适配 |
| **离线策略** | 纯前端 + 本地算法 + 本地数据打包 | 农历/八卦用算法本地计算；历史数据打包进包体 |
| **数据存储** | IndexedDB（结构化）+ localStorage（配置） | 浏览器/Node/Electron 环境通用，离线可用 |
| **置顶悬浮** | 宿主 overlay API + Tauri 桌面版兜底 | 宿主不支持真置顶时，独立桌面版作为增强 |

### 4.3 备选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **A. Web Components + 适配器（推荐）** | 跨宿主通用、体积小、标准、离线友好 | 各宿主适配器需分别写 | 多宿主长期演进 |
| **B. VS Code 扩展为核心** | 生态最成熟、API 最稳 | DeepSeek 桌面端不一定兼容 VS Code 扩展 | 只做 VS Code / MarsCode |
| **C. Tauri 独立桌面悬浮窗** | 真置顶、不依赖宿主、全平台 | 用户需额外安装一个 app | 作为 P2 增强，兜底不支持嵌入的宿主 |

## 五、关键技术设计

### 5.1 农历与节气算法（离线）

- **农历转换**：使用 `lunar-javascript` 或自研查表法（1900-2100 年农历数据表约 200KB），纯前端计算，零网络依赖
- **24 节气**：基于定气法（太阳黄经）公式计算，精度 ±1 分钟
- **八卦推衍**：按日期干支 + 内置算法生成每日卦象（卦画、卦名、卦辞、爻辞从本地 JSON 数据读取）

### 5.2 文化内容数据分层

| 层级 | 内容量 | 包体大小 | 说明 |
|------|--------|---------|------|
| L1 基础 | 365 条历史事件 + 24 节气 + 8 大节日 | ~500KB | MVP 必带，打包进安装包 |
| L2 扩展 | 1000+ 条历史 / 5000+ 诗词 | ~3MB | 二期可选内容包，单独下载 |
| L3 深度 | 多朝代时间轴 / 人物传记 | ~10MB+ | 远期，按需加载 |

### 5.3 Token 数据获取策略

| 方式 | 可行性 | 说明 |
|------|--------|------|
| **手动录入 + CSV 导入** | ✅ MVP 必做 | 不依赖任何宿主接口，离线可用 |
| **宿主 API 自动读取** | ⚠️ 待核实 | 需确认 DeepSeek / 豆包是否有公开用量查询 API |
| **请求拦截统计** | ❌ 不推荐 | 技术复杂且可能违反宿主服务条款 |

### 5.4 离线分发策略

- **Git 安装**：`git clone <repo>` → 按宿主执行 `npm run install:deepseek` / `code --install-extension`
- **内网分发**：Git 内网镜像 + 离线 zip 包（单文件 ≤ 5MB），内网可直接下载安装
- **版本更新**：git pull 或宿主内更新，内网环境支持手动导入新版本包

## 七、风险分级与应对

| 等级 | 风险 | 影响 | 应对方案 |
|------|------|------|---------|
| 🔴 **P0** | 目标宿主的插件 API 与预期不符 | 架构推倒重来 | Phase 0 先做 Spike 验证，选 2-3 个宿主分别跑通 Hello World |
| 🔴 **P0** | 八卦内容涉嫌封建迷信，内网部署有合规风险 | 产品定位被动摇 | 内容严格定位为"文化知识 + 生活启示"，不做任何预测/吉凶断言；提供合规审核开关 |
| 🟡 **P1** | Token 数据无法自动获取，功能价值打折 | 用户留存受影响 | MVP 用手动录入 + CSV 导入验证需求；二期探索宿主 API 或浏览器扩展拦截 |
| 🟡 **P1** | DeepSeek / 豆包官方 API 变动导致适配失效 | 维护成本高 | 适配器层薄封装，核心层与宿主解耦；变动只改适配器 |
| 🟡 **P1** | 历史内容质量与准确性不可控 | 产品口碑受损 | 建立内容来源标注机制；L1 数据精选权威来源；支持用户反馈纠错 |
| 🟢 **P2** | 多宿主适配工作量超预期 | 排期延迟 | 优先 DeepSeek，其余按需求排序逐步支持 |
| 🟢 **P2** | 离线包体过大 | 内网分发不便 | L2/L3 内容做按需加载，MVP 只带 L1（<1MB 核心 + 500KB 数据） |

## 九、下一步建议

1. **先对齐 6 个关键歧义**（尤其是 A1 嵌入形态 和 A2 八卦内容边界），确认后锁定 MVP 范围
2. **启动 Phase 0 Spike 验证**（1-2 周），用最小成本验证宿主 API 可行性
3. **确定首宿主优先级**：建议 DeepSeek 优先（用户最常用 + 社区文档较完善），VS Code/MarsCode 作为第二宿主
4. **组建最小团队**：1 名前端工程师（核心+适配器）+ 0.5 名内容编辑（L1 历史数据），即可启动 MVP
