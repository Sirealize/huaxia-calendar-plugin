# Phase 0-Spike B：核心算法可行性（@shishu/core）

> 任务：用实测证据回答「纯本地离线计算农历 + 节气 + 干支是否靠谱」，并交付可复用的核心模块原型。
> 日期：2026-11-18；实测环境：Node v24.16.0 / npm 11.13.0 / macOS（Intel i7-9750H）/ 北京时间为展示口径。
> 代码位置：`packages/core/`；相关脚本：`packages/core/scripts/`。

## 0. 结论先行

**Go：核心算法层完全可行，建议直接采用 vendor `lunar-javascript@1.7.8`（MIT）方案，自研查表法留作 M2 体积优化选项。**

| 问题 | 结论 | 硬数字（均为本机实测，非估算） |
| --- | --- | --- |
| 农历/节气/干支能否纯本地算？ | **能**，零联网、零后端、纯函数 | 10 年逐日遍历 3652 天仅 **757～1059 ms**（3 个 API/天，单日 0.21～0.27 ms） |
| 精度是否可信？ | **可信**，与香港天文台官方历表一致 | 2026 年 24 节气 **24/24** 与 HKO 一致到分钟；HKO 抽样 22 个完整年份 **8,035 天逐日：8,005 天一致，仅 2057 的 30 天差一天**（见 §6.5） |
| 体积是否可接受？ | **可接受**，桌面侧栏场景无压力 | vendor `lunar.js` 436,585 B（426 KB），gzip -9 后 **108 KB**；minify+gzip 后 100,351 B（≈98 KiB） |
| 许可证是否允许 vendor？ | **允许** | MIT（`Copyright (c) 2018 6tail`），可商用、可修改、可再分发，仅需保留版权与许可声明（已随包保留 `LICENSE`） |
| 是否要自研？ | **Spike 阶段不建议** | 自研「能算但不能算准」：农历日期表本身很小（实测参考 800 B 二进制/1,599 B 文本），但**精确节气时刻需要天文算法**；自研 = 自建天文算法 + 全区间权威数据校验，成本远高于节省的 ~70 KB |
| 干支口径 | **默认立春精确时刻**，同时提供三种口径 | 以 2026 为例：02-05～02-16 期间立春口径为丙午、春节口径为乙巳，**差一整年**；02-04 当天 0 点与 04:02:08 之间差一个时刻 |
| 数据层 | 节日/农历/节气日期**可算**；历史事件文本、卦辞爻辞、白话解读、调休**必须靠数据** | L1 内容包（366 条历史事件 + 64 卦 + 10 节日）实测 **354.0 KB JSON，gzip 后 139.8 KB** |

**一句话**：算法层不是风险；真正的风险在**内容版权（CC BY-SA）**与**未来日期官方口径对齐**（2057 类边界），这两条已写进 §5.3 与 §6.5。

| API | 返回 |
| --- | --- |
| `solarToLunar(input)` | 农历年/月/日、是否闰月、中文月名日名、生肖、春节口径干支、星期、年内日序 |
| `getGanZhi(input, options?)` | 年/月/日/时干支 + 生肖；年干支三口径，日干支两日界 |
| `getSolarTerms(year)` | 24 节气：名称、节/气、视黄经、北京时间日期时刻、ISO、epochMs |

设计要点：

- `engine.ts` 是**唯一**直接 import vendor 的模块，上层 API 与 vendor 解耦；将来换自研实现只改这一层。
- 全部 API 纯函数，不读写全局状态、不联网；入参为 `{year,month,day,hour?,minute?,second?}`（北京时间口径）或 `Date`（按宿主本地字段解释）。
- 时间以「北京时间的日历字段 + 显式 epochMs/ISO」双形态返回，避免跨时区日界问题（§6.1）。

## 2. 选型对比：vendor `lunar-javascript` vs 自研查表法

### 2.1 候选

| 维度 | A. vendor `lunar-javascript@1.7.8`（**采用**） | B. 自研农历/节气查表法 |
| --- | --- | --- |
| 产物形态 | 单文件 UMD `lunar.js`，无 ESM 子路径 | 自建 TS 模块 + 数据表 |
| 体积（实测） | `lunar.js` 436,585 B；gzip -9 **110,696 B**；esbuild minify 331,237 B；minify+gzip **100,351 B**；npm tarball 123,554 B | 农历日期表：经典 1900-2099 表 200 条 int 实测 800 B（二进制）/1,599 B（十六进制文本）；节气表：4,824 条（201 年 × 24），紧凑编码约 **15-20 KB 二进制**（**估算，按编码方案推算**）；JSON 形式约 190-200 KB（即任务里「约 200KB」的来源）。算法代码另计约 5-10 KB |
| 精度 | 已验证：农历与 HKO 抽样 22 个完整年份 8,035 天中 8,005 天一致（仅 2057 的 30 天差一天）；2026 节气 24/24 HKO 分钟级一致；精确时刻与香港天文学会年历差 <1 秒 | 精度**取决于自建数据源**：若用手工/开源表（多为 GPL 派生的经典万年历表），1933/1954/1978/2057 等午夜朔边界容易与官方差一天（本 Spike 实测到 446 天二源分歧，见 §3.4）；且开源表很难覆盖「精确时刻」 |
| 节气精确时刻 | **有**（秒级，北京时间），可支撑干支纪月/纪年**时刻边界** | 纯查表只能给「日期」或预存时刻；精确时刻需自建 VSOP87/DE 星历计算（工程量≈重写本库核心） |
| 干支/八字扩展 | 自带干支、时辰、十神等，后续 M1/M2 扩展成本低 | 需自研 60 甲子、节气换月、23 点换日等规则并逐条验证 |
| 维护成本 | 低：pin 版本 + 手动升级；已有自动化测试兜底 | 高：数据源更新、历史/未来边界裁决、闰月规则、跨 1900/2100 边界都要长期维护 |
| 许可证 | **MIT**，可商用/可再分发（已核实并保留 LICENSE） | 自研代码可自选许可；但**数据表来源有坑**：经典 1900-2100 农历表常见于 GPLv2 派生库（如 Python `lunardate`，文件头标明 GPLv2），不能直接抄入 MIT 项目；从 HKO 官方数据重建需处理政府数据版权/署名与自动化流水线 |
| tree-shaking | **不支持**：UMD 单文件 IIFE，无 `exports`/`module` 字段，打包器无法裁剪；用只用 1 个 API 也要带上 436 KB | 支持，只打包用到的数据/逻辑 |
| 离线安装 | `dependencies` 为空（已 vendor），`npm install` 不需要网络、不受 registry 影响 | 同样离线，但需自建数据打包流程 |
| 可靠性背书 | 上游 6tail/lunar-javascript 长期维护、广泛使用；本 Spike 独立复核通过 | 无第三方复核，需自建验收 |

### 2.2 取舍结论

1. **M0/M1 采用 vendor**。理由按权重排序：
   - 精度已被独立数据源（HKO 官方历表 + 独立天文实现 astronomy-engine + 香港天文学会年历）验证；
   - 节气**精确时刻**是产品刚需（干支换年/换月、节气卡片倒计时），自研查表给不了；
   - MIT 许可可合规 vendor，离线安装零依赖；
   - 110 KB gzip 对桌面插件（VS Code 扩展/Tauri 侧栏）是可接受量级；若宿主是极受限 WebView，可再评估。
2. **保留自研可能**：`engine.ts` 是唯一 vendor 耦合点；M2 若 bundle 体积成为瓶颈，可评估「自研日期表 + 预生成节气时刻表」。届时的验收基线就是本 Spike 的 44 个测试 + HKO 交叉校验脚本，可无缝迁移。
3. **不建议**为了体积在 M0 自研：节省约 70-90 KB（gzip），换来的是自建天文算法或全区间权威数据+长期裁决成本，性价比不成立。

> 注：`lunar-javascript` 无 TypeScript 类型，`src` 侧手写了最小声明 `vendor/lunar-javascript/lunar.d.ts`；`tsc --noEmit` 实测 0 错误。

裁决汇总：446 个分歧日中，本库被 HKO 判为正确 **416 天**（1933 的 30 天 + 1954 的 30 天 + 1978 的 30 天 + 2100 的 326 天），只剩 **2057 年的 30 天**与 HKO 差一天。

综合：73,384 天里，本库与「官方/表驱动」两源在 **73,354 天（99.959%）** 上一致或经裁判为正确；仅 **2057 年 30 天（0.041%）** 与 HKO 差一天。

### 3.5 干支纪年三种口径的实测差异（项目推荐口径：立春精确时刻）

以 2026 年为例（立春 = 2026-02-04 04:02:08，春节 = 2026-02-17）：

| 公历日期/时刻（北京时间） | 立春精确时刻（默认） | 立春当天 0 点 | 春节（正月初一） |
| --- | --- | --- | --- |
| 2026-02-03 00:00 | 乙巳 | 乙巳 | 乙巳 |
| 2026-02-04 00:00 | **乙巳** | **丙午** | 乙巳 |
| 2026-02-04 04:02:07 | 乙巳 | 丙午 | 乙巳 |
| 2026-02-04 04:02:08 | **丙午** | 丙午 | 乙巳 |
| 2026-02-05 ～ 02-16 | **丙午** | 丙午 | **乙巳** |
| 2026-02-17 起 | 丙午 | 丙午 | 丙午 |

- 「差一天」：02-04 当天，日期口径（当天 0 点换年）与精确时刻口径（04:02:08 换年）结果不同。
- 「差一年」：02-05～02-16 期间，立春口径已是丙午马年，春节口径仍是乙巳蛇年。
- **项目推荐口径：立春精确时刻**（传统历法/命理标准，且与节气体系自洽）；API 同时返回三种口径字段（`yearByLiChun` / `yearByLiChunDay` / `yearByLunarNewYear`），UI 可在设置中切换。
- 注意自洽性：`solarToLunar()` 返回的农历年/生肖/干支固定用**春节口径**（因为农历年本身以正月初一为界）；干支展示用 `getGanZhi()` 的立春口径。两者在 02-05～02-16 会「看起来不一致」，这是口径差异而非 bug，UI 需明确标注。

### 3.6 10 年逐日模糊测试（2026-01-01 ～ 2035-12-31，3,652 天）

对每一天依次调用 `solarToLunar` / `getGanZhi` / `getFestivals`，并逐年校验 24 节气，断言：

1. 无异常、无 NaN/空值；农历月 1-12、日 1-30、星期/年内日序自洽；

### 5.2 Schema 概要

TypeScript 接口全量定义见 `src/data/schemas.ts`，示例 JSON 见 `src/data/samples/`，校验器见 `src/data/validate.ts`。

**HistoricalEvent（历史事件）** —— 关键：许可证字段强制。

```ts
interface HistoricalEvent {
  id: string;                       // 'he-0217-001'
  solar: { month: number; day: number };  // 归档键：公历月日（跨年每日）
  eventYear: number;                // 事件发生年，负数=公元前
  yearLabel: string;                // '1949 年'
  title: string;                    // 8-20 字
  summary: string;                  // 建议 60-140 字
  category: HistoricalEventCategory;
  tags?: string[];
  weight?: number;                  // 同日排序 0-100
  source: string;                   // 【强制】来源名
  sourceUrl?: string;               // 【可选】来源链接
  license: LicenseId;               // 【强制】'CC-BY-SA-4.0' | 'self-authored' | 'public-domain' | ...
  attribution?: string;             // CC 许可要求展示的署名
  retrievedAt?: string;             // ISO 日期，溯源用
}
```

**Hexagram（卦象）**：`id 1-64`、`name`、`symbol`（Unicode ䷀…）、`binary`（6 位，自下而上，1=阳）、`guaCi`、`tuanCi?`、`xiangCi?`、`yaoCi[6]`、`yongCi?`（乾坤）、`interpretation`（原创白话）、`themes`、`source/license` 强制。
仓库内置 64 卦**骨架**（卦序/卦名/符号，公有领域事实，`HEXAGRAM_SKELETONS`，实测 2.4 KB），文本内容由内容包补。

**CustomFestivalDef（自定义节日）**：规则类型 `solar-fixed` / `lunar-fixed` / `solar-term` / `nth-weekday`（如母亲节=5 月第 2 个周日）。法定节假日标记可加，但**调休仍需数据**。

**ContentPackManifest（内容包清单）**：`schemaVersion`、`packId/packVersion`、`counts`、`coverage.years`、`files[{path,bytes,sha256,recordCount}]`、`attribution`（必须随包展示的署名）。

### 5.3 许可证是强制字段（合规约束，必须落地）

这是本 Spike 发现的最重要**非技术**风险：

- 「历史上的今天」类公开数据集绝大多数源自维基百科（**CC BY-SA 4.0**）。把这类内容打包进离线安装包并分发给用户，会产生两项义务：
  1. **署名**：必须展示来源与作者（`attribution` 字段）；
  2. **相同方式共享**：内容包（作为衍生作品）需以 CC BY-SA 4.0 兼容方式分发。
- 现仓库的许可证策略（待项目负责人拍板）：
  - **可随包自由分发**：`self-authored`（原创）、`public-domain`（如《周易》经文）、`CC0-1.0`、`MIT`；
  - **随包分发需署名**：`CC-BY-4.0`（`attribution` 必填）；
  - **随包分发需署名 + 相同方式共享**：`CC-BY-SA-4.0`。若产品不接受内容包整体 CC BY-SA 分发，则**不得随安装包分发**维基来源内容，只能：
    a) 内容团队**原创改写**（事实不受版权保护，但表达必须重写，可标 `self-authored`）；
    b) 做成运行时**可选的在线/用户自装内容包**，不进入默认安装包；
    c) 与来源方另行取得授权。
- 代码层已强制：`validateContentPack()` 把缺失 `source`/`license` 或 `license='unknown'` 判为 **error，阻断发布**；CC 许可条目缺 `attribution` 判为 warning（发布前必须清零）。测试已覆盖。

> 建议默认内容包策略：**全部原创 + 公有领域**（`self-authored`/`public-domain`），把 CC BY-SA 内容隔离为可选订阅包，避免整个产品被 ShareAlike 传染。此项需要产品/法务确认后再开始内容生产。

### 5.4 L1 内容包体积实测（按 schema 真实序列化）

测量对象：366 条历史事件（覆盖闰年 366 个公历月日）+ 64 卦 + 10 条自定义节日 + manifest。
文本为**占位文本**（字段结构/字段数与真实包一致，文本长度按真实文案分布抽样：标题 8-20 字、摘要 90-130 字、解读 100-160 字）。占位文本为随机汉字，gzip 压缩率低于真实中文文案，因此 **gzip 数字是保守上界**；JSON 紧凑字节数与文本内容无关，**精确可复现**。

| 数据文件 | 条数 | JSON 紧凑 | gzip -9 | 单条平均 |
| --- | ---: | ---: | ---: | ---: |
| historical-events.json（完整字段） | 366 | 268,551 B（262.3 KB） | 94.2 KB | 734 B |
| hexagrams.json（64 卦全文本字段） | 64 | 90,748 B（88.6 KB） | 45.3 KB | 1,418 B |
| festivals.json | 10 | 2,751 B（2.7 KB） | 1.1 KB | 275 B |
| manifest.json | 1 | 417 B | — | — |
| **整包（含 manifest）** | — | **362,526 B（354.0 KB）** | **143,173 B（139.8 KB）** | ≈989 B/条 |
| 精简字段变体（省略 sourceUrl/attribution/retrievedAt） | 366 | 311,668 B（304.4 KB） | 139,638 B（136.4 KB） | 850 B |
| 64 卦骨架（仅 id/name/symbol） | 64 | 2,469 B | 约 0.6 KB | 39 B |

结论/建议：

- L1 包按「366 事件 + 64 卦」全量约 **350 KB JSON / 140 KB gzip**，与核心库打包产物（minify+gzip ≈104.5 KB）相加约 **245 KB gzip**，对离线安装包完全可接受；
- 体积大头是历史事件文本（262 KB / 366 条）与卦象全文本（88.6 KB / 64 卦）；**卦辞爻辞是可预见的第二大头**，若预算紧张可先上「64 卦骨架 + 60 字解读」，全文本后续按需加载；
- 体积可由内容团队用同一脚本对真实数据复测：`node scripts/estimate-content-size.ts /path/to/real-pack-dir`（约定 `historical-events.json` / `hexagrams.json` / `festivals.json`）。

## 6. 已知坑（按风险从高到低）

### 6.1 时区：所有时刻按北京时间（UTC+8），`Date` 入参有宿主时区风险

- `lunar-javascript` 的节气时刻按**北京时间**存储/计算；本库对外统一声明 UTC+8，并返回 `iso`（如 `2026-02-04T04:02:08+08:00`）与 `epochMs`（绝对时刻）。
- `Date` 入参按**宿主本地时区**读取年月日时分（等价 `date.getFullYear()`）；在非 UTC+8 机器上，跨日时刻可能与北京时间日界不一致。**对时区敏感的调用请用显式字段**（`{year,month,day,hour,minute,second}`）。插件宿主以国内用户机器为主，风险低，但 SDK/服务端场景必须注意。
- 中国 1986-1991 年实行过夏令时（+9）。本库不处理历史民用时制，一律北京时间 UTC+8；影响仅限「历史日期精确时辰/小时」展示，不影响农历日期与节气日期（日界以北京时间为准，与官方历表一致）。

### 6.2 干支换年/换月/换日口径（必须显式选择并标注）

- 年：`li-chun`（默认，立春精确时刻）/ `li-chun-day`（立春当天 0 点）/ `lunar-new-year`（正月初一）；差异见 §3.5。
- 月：`month`（节令精确时刻换月）/ `monthByDay`（节令日期换月）；立春当天 0 点与 04:02:08 之间结果不同（己丑 vs 庚寅）。
- 日：`day`（0 点换日）/ `dayByZiHour`（23:00 子时换日）；2026-02-17 23:00 后两者分别为壬戌/癸亥。
- 产品必须明确「显示的干支按哪套口径」，否则用户会认为有 bug。

### 6.3 农历边界与闰月命名

- 支持范围：算法可跑 1-9999 年；**已验证范围为 1901-2100**（`VERIFIED_YEAR_RANGE`）。1900-01-31 是经典万年历起点，1900 年 1 月 1-30 日属 1899 年农历，超出常见表范围；2100 年之后未做权威校验，对外展示应标注「未校验」或限制范围。
- 闰月命名：本库采用规范写法「闰十一月/闰十二月」（与 HKO 一致），另提供口语别名「冬月/腊月」（`lunarMonthAlias`）；不要写成「闰冬月」。
- 闰月不过节：闰五月初五不是端午（2028-06-27 实测不触发端午节），闰月不重复过任何农历节日。
- 除夕日期不固定（腊月廿九或三十），必须按「次日是否正月初一」判定，禁止写死 12-30。

### 6.4 vendor 的节气表键名有「别名键」

`lunar-javascript` 的 `getJieQiTable()` 为避免跨年同名字典键冲突，对「下一年度的前几个节气 / 上一年度的大雪」使用英文别名键（`DONG_ZHI`、`XIAO_HAN`、`DA_HAN`、`LI_CHUN`、`YU_SHUI`、`JING_ZHE`、`DA_XUE`），且同一张表里「冬至」可能是上一年度的。本库 `solar-terms.ts` 做了别名映射 + 按公历年份过滤 + 去重 + 数量断言（不足 24 直接抛错），并在测试中对 2026/2027/1901-2100 抽样验证 24/24 齐全。**直接拿 `getJieQiTable()[name]` 会踩到跨年错位。**

### 6.5 2057 年：未来日期与官方预测差一天（真实风险）

- HKO 官方历表：**九月初一 = 2057-09-28**；本库：**九月初一 = 2057-09-29**；该月 30 天错位后自动恢复一致。
- 独立天文计算：朔（新月）发生在 **2057-09-29 00:00:40 北京时间**，距午夜仅 **40 秒**。即：官方预测的朔在 9/28 23:59:xx，寿星天文历/astronomy-engine 在 9/29 00:00:40；差异由星历/ΔT 模型造成，属**预测边界不可消除的分歧**。
- 同类风险：2027 春节的朔发生在 **2027-02-06 23:56:47**（距午夜 3 分 13 秒），若未来官方模型微调，2027 春节存在理论上的日期调整风险（HKO 现口径确认为 2/6）。
- 建议：日常使用（2026-2035 已逐日验证）无影响；若产品要展示 2050 年后官方日期，应引入「官方历表覆盖表」机制（`engine.ts` 增加 override 数据），并明确数据来源与版本。

### 6.6 1901-1918 年 3 个节气日期与 HKO 历史表不一致

- 1912 小雪：本库 1912-11-22 23:48:08；astronomy-engine 23:48:22；HKO 表记为 11/23。
- 1913 秋分：本库 1913-09-23 23:52:41；astronomy-engine 23:52:35；HKO 表记为 9/24。
- 1917 大雪：本库 1917-12-08 00:00:59；astronomy-engine 00:01:01；HKO 表记为 12/7。
- 结论：这 3 处本库与**现代天文计算**一致，HKO 历史表与其不同（历史历书数据/ΔT 差异），且都发生在交节时刻距午夜 ±12 分钟内。属「历史权威数据源分歧」；本次抽样的 1920 年后年份未发现同类分歧，但不排除未抽样年份存在。若产品要做「历史精确节气」，需定义口径并可能引入 override 表。

### 6.7 节气时刻精度：适合日历产品，不适合天文用途

与 astronomy-engine（JPL 星历）比，2026 年 24 节气时刻差最大 41 s、平均 19.7 s；与香港天文学会《香港天文年历 2026》的公开时刻差 <1 s。产品展示分钟级足够；若有「交节时刻精确到秒」的需求，应声明精度约 ±1 分钟。

### 6.8 性能与缓存

- 单次调用 0.05-0.10 ms，无需缓存；但 `getSolarTerms(year)` 内部会构造 vendor Lunar 对象（~0.1 ms/年），UI 若一次渲染 200 年时间轴需 ~200 ms，建议加缓存或放 worker。
- `getSolarTermOn` 内置按日缓存（上限 4096 条），批量渲染安全。

### 6.9 工程/合规坑

- **UMD 不可 tree-shake**：只要 import 任何 API，打包产物都会带上 436 KB（gzip 108 KB）。若宿主 bundle 预算极紧，这是唯一需要重新评估自研的场景。
- **vendor 升级必须同步 LICENSE + sha256 + 测试**：流程见 `VENDOR.md`；`lunar.js` 禁止手改。
- **内容许可证**：见 §5.3，必须在内容生产启动前拍板，否则后期返工成本极高。
- **数据校验是发布闸门**：`validateContentPack()` 已把许可证/64 卦完整性/计数一致性设为 error，内容流水线必须调用。

## 7. 结论与待决策清单

**结论**：核心算法层 Go。`@shishu/core` 已达到「可运行、可测试、可复现、精度有据」的 Spike 目标，可以进入 M0 集成。

请项目负责人确认以下 6 件事：

1. **依赖方案**：批准 vendor `lunar-javascript@1.7.8`（MIT）进仓库（已 vendor + `VENDOR.md` 审计信息），M0 不再引入 npm dependencies。
2. **干支口径**：批准默认「立春精确时刻」+ 保留三口径字段；UI 需标注口径。
3. **内容许可证策略**：CC BY-SA（维基来源）内容是否允许随安装包分发？建议默认内容包全原创/公有领域，CC BY-SA 内容做可选订阅包（§5.3）。
4. **范围声明**：对外声明「已验证 1901-2100」，2050 年后官方日期如需绝对权威，M2 增加官方历表 override。
5. **体积预算**：核心 gzip 108 KB + L1 内容 gzip 140 KB ≈ 250 KB；确认宿主（VS Code 扩展/Tauri/WebView）预算可接受。
6. **精度口径**：节气展示到分钟即可（本库秒级精度，与官方年历差 <1 s）；不承诺天文级精度。

后续（M0/M1）建议：
- 把 `packages/core` 设为 npm workspace（`@shishu/core`），宿主壳直接 import TS 源码打包；
- 内容流水线接入 `validateContentPack` 作为 CI 发布闸门；
- 增加 `verify-against-hko.mjs` 到月度 CI（可选，需网络），监控上游升级/边界回归；
- 若要支持 2050+ 官方日期，设计 `official-almanac-overrides.json`（年份→农历/节气修正），数据来自 HKO/紫台并标注版本。
